# 회의록·화자 분리 기술 검토 (2026-09-29)

받아쓰기 앱에 회의록 기능을 넣을 수 있는지 재 본 기록이다. **결론: 된다.** 네 가지 미지수를
전부 실측으로 지웠고, 걱정했던 "빌드를 갈아엎어야 한다"는 사라졌다.

재는 데 쓴 것: 35분짜리 한국어 팟캐스트(2120초, 두 사람 대화).

## 실측 결과

| | 걸린 시간 | 실시간 대비 |
| --- | --- | --- |
| 애플 서버 인식 — 35분 통째로 | 22분 넘게, **못 끝냄** | — |
| 애플 서버 인식 — 5분씩 잘라 7조각 | 274초 | 7.7배 |
| **whisper.cpp large-v3-turbo-q5_0** | **124초** | **17배** |
| whisper.cpp — 60초 조각만 | 1.9초 | **30배** |
| **sherpa-onnx 화자 분리** | **178초** | **12배** |

글자 수는 애플 10,515자 / Whisper 16,399자. **Whisper 가 더 빠른데 1.5배 더 받아썼다.**

화자 분리 결과는 화자0 18.9분 / 화자1 17.4분 / 화자2 0.7분. 두 사람이 반씩 말하는 팟캐스트와 맞는다.

## 정해진 것

- **받아쓰기는 whisper.cpp.** 애플 서버 인식은 긴 파일에서 비선형으로 느려진다(5분 34초 → 35분은 22분+).
  짧은 받아쓰기(`fn⌃`)는 지금 그대로 두고, 회의록만 별도 경로로 간다.
- **화자 분리는 sherpa-onnx.** pyannote 분할 + 화자 임베딩.
- **둘 다 순수 C API 라 `swiftc` 에 그대로 붙는다.** SwiftPM 도 Xcode 프로젝트도 필요 없다.
  WhisperKit·FluidAudio 는 SwiftPM 패키지라 빌드를 갈아엎어야 했는데, 이 경로엔 그 문제가 없다.
  Sparkle 처럼 `vendor/` 에 넣으면 된다.
- 모델 크기: 받아쓰기 547MB + 화자 분리 45MB. 번들에 못 넣으니 **회의록을 켤 때 받는다.**
  안 켜면 지금과 같다(앱 6.3MB, DMG 1.8MB).
- 변동비 0원. 네트워크도 필요 없다 — "회의 내용이 밖으로 안 나간다"가 무료 앱의 셀링 포인트가 된다.

## 실제 체감 시간

35분 회의를 통으로 나중에 처리하면 받아쓰기 70초 + 화자 분리 180초 + 요약 30초 ≈ **5분**이다.
다만 **받아쓰기는 회의 중에 실시간으로 끝나 있고 화자 분리도 미리 돌릴 수 있어서**,
회의가 끝난 뒤 기다리는 시간은 그보다 훨씬 짧다.

## 함정

- ⚠️ **명령줄 도구를 따로 만들면 TCC 가 죽인다.** `Info.plist` 에
  `NSSpeechRecognitionUsageDescription` 이 없으면 프로세스가 강제 종료된다(exit 134).
  그래서 받아쓰기 진단은 앱 안의 `--transcribe` 플래그로 넣었다.
- ⚠️ **`SFSpeechRecognizer` 는 결과를 메인 큐로 보낸다.** 진단 플래그처럼 메인 스레드를
  세마포어로 막고 기다리면 결과가 영영 안 온다(60초 소리로 400초를 기다렸다).
  `recognizer.queue = OperationQueue()` 로 옮겨야 한다.
- ⚠️ **ggml 백엔드(Metal 등)는 별도 `.so` 로 분리돼 있다.** 명령줄 도구는 알아서 불러오지만
  라이브러리로 쓰면 안 해 준다. `ggml_backend_load_all_from_path()` 를 직접 불러야 하고,
  안 부르면 모델을 여는 순간 `GGML_ASSERT(device) failed` 로 죽는다.
- ⚠️ **화자 수를 자동으로 못 잡는다.** 임계값(0.5)에 맡겼더니 450명으로 쪼개졌고,
  `num_clusters=3` 으로 고정하니 제대로 나왔다. 임베딩 모델을 중국어용으로 쓴 탓일 수 있어
  튜닝 여지는 있지만, **사용자에게 참석 인원을 묻는 게 현실적이다** — 어차피 화자 이름은
  사람이 붙여야 한다(화자0 → 김부장).
- 애플 인식도 낱말마다 시간 정보를 준다(60초에서 82개 중 82개, 5분에서 411개 중 411개).
  화자 구간과 겹쳐 맞추는 데 쓸 수 있다 — 다만 속도 때문에 whisper.cpp 로 간다.

## 진입점은 메뉴바로 정했다 (2026-09-29)

회의록은 **단축키로 시작하지 않는다.** 메뉴바 아이콘에서 "회의 녹음 시작"을 누른다.

지금 단축키(`fn⌃`)는 `recorder.isRunning ? stopAndPolish() : startRecording()` 하나로 토글이고,
손에 익어서 반사적으로 누르는 키다. 회의 중에 습관적으로 누르면 **회의 하나가 통째로 끊긴다.**
받아쓰기는 잘못 눌러도 별일 없지만 회의록은 그렇지 않다.

회의는 한 번 시작하면 오래 가니까 **시작하는 데 1초 더 걸리는 것이 문제가 안 된다.**
그 대신 실수로 켜고 끌 일이 없어진다. 녹음 중에는 메뉴바 아이콘을 바꾸고 경과 시간을 보인다.

별도 단축키(`⌃⌥M` 같은)는 외울 키가 늘고 오작동 위험이 남아서 뺐다.
같은 키를 길게 누르는 방식은 `fn⌃` 이 수정자 키만 쓰는 방식이라 구분이 까다롭고 사용자가 헷갈린다.

⚠️ **단축키보다 결과를 어디로 보낼지가 더 큰 일이다.** 받아쓰기는 커서에 꽂는 게 전부지만
   30분치 텍스트는 커서에 붙여넣을 수 없다. 저장할 곳과 다시 볼 화면이 필요하다.
   지금 메뉴바의 기록 보기 화면은 회의록을 담기엔 작다. 실제로는 이쪽이 작업량이 더 많다.

## 아직 안 한 것

- **소리를 보관하지 않는다.** `IntonationTracker` 가 마지막 6초만 메모리에 들고 있고,
  주석에 "목소리를 디스크에 남기지 않는다"고 못 박혀 있다. 화자 분리는 녹음 전체가 필요하므로
  이 결정을 뒤집어야 한다. 기술이 아니라 제품 결정이다.
- 요약 분량은 35분에 1만~1만6천 자다. 한 번에 넣을 수 있는 크기라 요약 비용 걱정은 줄었다.
  다만 Gemini 무료는 모델당 하루 20회라, 회의록을 자주 쓰면 거기서 먼저 막힌다.

## 시스템 소리 잡기 — 된다 (2026-09-29)

`SystemAudio.swift` 가 `ScreenCaptureKit` 으로 스피커로 나가는 소리를 잡는다.
화상회의에서 **상대방 목소리**가 여기로 들어온다 — 마이크에는 내 목소리만 들어오기 때문이다.

끝까지 이어서 확인했다. 스피커로 한국어를 말하게 하고 그것을 잡아 받아쓴 결과다.

    버퍼 733개, 최대 진폭 0.8474
    → "안녕하세요. 오늘 회의 시작하겠습니다. / 첫 번째 안건은 다음 분기 예산입니다.
       / 네, 확인했습니다. 마감은 다음 주 금요일로 하겠습니다."

문장부호까지 맞게 나왔다. 진단은 `--capture-system-audio <초> <출력.wav>` 로 다시 돌릴 수 있다.

- 화면은 안 쓰지만 **필터에 디스플레이가 있어야 한다.** 2×2 로 두고 프레임 간격을 1초로 잡아 일을 줄였다.
- ⚠️ `excludesCurrentProcessAudio` 를 빼면 **우리가 낸 소리가 되돌아 들어와 섞인다.**
- ⚠️ **화면 기록 권한이 필요하다.** 없으면 `SCShareableContent` 가 오류를 던진다.
  첫 실행 안내에 이 권한을 넣어야 한다 — 마이크·손쉬운 사용에 이어 세 번째다.
- 버퍼가 0개면 권한 문제, 버퍼는 있는데 진폭이 0 이면 권한은 났지만 소리가 안 잡히는 것이다.
  진단 플래그가 이 둘을 갈라서 알려 준다.

## 두 갈래로 녹음하기 — 되지만 함정이 둘 (2026-09-29)

`MeetingRecorder.swift` 가 마이크(나)와 시스템 소리(상대)를 **따로** WAV 로 남긴다.
16kHz 모노 int16 — whisper.cpp·sherpa-onnx 가 그대로 받는 형식이고, 1시간 두 트랙에 220MB 다.
48kHz 스테레오 float32 로 두면 2.6GB 라 긴 회의를 감당 못 한다.

보관 위치: `~/Library/Application Support/Brefly/meetings/<날짜-시각>/{mic,system}.wav`

⚠️ **이 앱은 원래 목소리를 디스크에 남기지 않는다.** 회의록은 그 원칙의 의도적인 예외다.
   받아쓰기(`fn⌃`)는 지금처럼 아무것도 남기지 않는다.

### 함정 1 — 스피커 소리가 마이크로 되돌아 들어온다 (아직)

두 갈래를 따로 받아썼더니 **같은 문장이 양쪽에 다 있었다.** 그대로 두면 회의록에 상대의 말이
두 번씩 적힌다. 혼자 있는 방에서 노트북 스피커로 회의하는 것이 보통이라 **이어폰을 전제할 수 없다.**

`AVAudioInputNode.setVoiceProcessingEnabled(true)` 로 고치려다 실패했다. **목소리까지 깎는다.**
사람이 같은 크기로 말하면서 잰 값이다.

| 설정 | 마이크 최대 | 형식 |
| --- | --- | --- |
| 에코 제거 끔 | **0.0756** | 48000Hz 1ch |
| 에코 제거 켬 | 0.0029 | 48000Hz **5ch** |
| 에코 제거 켬 + 믹서 경유 | 0.0000 | 44100Hz 2ch |
| 에코 제거 켬 + 출력 연결 | 엔진 시작 실패 (-10875) | — |

26배 작아졌고, **5채널 모두 같은 값이라 채널을 잘못 고른 것도 아니다.** 켜면 회의록에
쓸 수 없는 소리가 된다. 다시 켜지 말 것.

**대신 글자 단계에서 거른다.** 마이크에 섞인 에코는 같은 시각 시스템 트랙에 있는 것과
**같은 말**이다. 두 트랙을 각각 받아쓰면 낱말마다 시각이 나오므로, 시간으로 맞춰 겹치는 것을
빼면 된다. 오디오 API 와 씨름하는 것보다 확실하고 하드웨어를 안 탄다.
남는 한계는 **내가 상대와 동시에 말할 때**인데, 그건 화자 분리도 똑같이 겪는 문제다.

### 함정 2 — 시스템 캡처는 모든 앱 소리를 잡는다 (안 고침)

회의와 무관한 브라우저 재생 소리가 그대로 섞여 들어왔다. 회의록에 유튜브 소리가 들어간다는 뜻이다.
`SCContentFilter` 는 앱을 골라 담을 수 있으므로 **"어느 앱 소리를 들을지" 고르는 화면**이 필요하다
(줌·미트·슬랙 등). 지금은 아무것도 안 거르고 전부 받는다.

### 함정 3 — Whisper 는 무음에서 말을 지어낸다 (안 고침)

에코를 지운 뒤 완전한 무음이 된 마이크 트랙을 받아썼더니, 그럴듯한 한 문장이 나왔다.
회의 중 조용한 구간마다 없는 말이 적힐 수 있다. **무음 구간을 미리 걸러내야 한다**(VAD).
